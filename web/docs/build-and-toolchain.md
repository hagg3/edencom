# Build & Toolchain (Web Port)

Not covered by the root docs at all — this is a new topic specific to the web port.

## Toolchain
Emscripten SDK, vendored at `web/emsdk/` (gitignored) — version 3.1.74 as of this
writing. `source ./emsdk/emsdk_env.sh` before building. This is the port's equivalent
of the root project's Xcode/iOS SDK dependency.

## Build variants
```
cd web && source ./emsdk/emsdk_env.sh
cmake --build build-st -j8     # -DEDEN_THREADED=OFF — single-threaded, the one actually
                                # used/runnable day to day
cmake --build build-rel -j8    # release build (see sizes below), reachable via
                                # eden-st.html?build=rel
emcmake cmake -B build-thr -DCMAKE_BUILD_TYPE=Debug -DEDEN_THREADED=ON && \
  cmake --build build-thr -j8  # the THREADED build (audit row 36/C1, pass 63), reachable via
                                # eden-st.html?build=thr
```
`EDEN_THREADED` defaults **OFF** (audit row A1) and is `-pthread -sPTHREAD_POOL_SIZE=4`
— **not** `PROXY_TO_PTHREAD`/OffscreenCanvas, whatever older prose says: engine, GL and
DOM all stay on the browser main thread, and the flag exists to make `pthread_create`
real (the world-load thread) and to enable a future meshing pool. The OffscreenCanvas
plan was measured, not reasoned, into the ground — see the `if(EDEN_THREADED)` block in
`CMakeLists.txt` and `../../WORKING/c1-threaded-build-handoff.md`.

That build's wasm memory is a `SharedArrayBuffer`, so its page must be **cross-origin
isolated** (`COOP: same-origin` + `COEP: require-corp`). `tools/serve.js` sends both;
`python3 -m http.server` does not. GitHub Pages cannot send response headers at all, so
`public/eden-coi.js` + `service-worker.js` synthesise them for a `?build=thr` navigation
and reload once (pass 65). `node tools/serve.js <port> --no-coi` withholds the real
headers to exercise that path locally, and `?coi=off` disables it entirely.
`EDEN_THREADED` (`CMakeLists.txt:39`) is a **build flag, not a source fork** —
deliberately kept that way so engine code stays thread-agnostic. See
[execution-flow.md](execution-flow.md) for how the single-threaded build's world-load
pthread is emulated synchronously.
Serve from `web/` (paths are relative): `python3 -m http.server 8123` — **use a fresh
port after every rebuild**, browsers aggressively cache `.wasm`/`.js`. Open
`http://localhost:8123/public/eden-st.html`.

For anything closer to a real deployment (perf-audit row 10/Q8 — measuring cold-start
size, or just wanting the ~69 MB payload to actually compress), `node tools/serve.js
[port] [root]` is a drop-in alternative from `web/` — same fresh-port-after-rebuild
caveat applies (it sends `Cache-Control: no-cache, must-revalidate` + an mtime/size
ETag, not far-future immutable caching, deliberately: `eden.wasm`/`eden.data`/
`Eden.eden` are unhashed literal filenames the Emscripten glue references directly, so
true immutable caching would need a build-time hashing step this doesn't attempt) but
Brotli/gzip-compresses `.wasm`/`.data`/`.eden`/`.js`/`.html` on the fly (cached in
memory, keyed on mtime+size) and answers `304` on a matching `If-None-Match`. See the
file's own header comment for the reasoning.

Headless logic check (no browser needed): `(cd build-st && node eden.js)`. Expect
`[eden-gl] no canvas '#eden-canvas'` then three `[eden-p1] tick N: World::update
returned` lines; anything else is a regression. The non-`MODULARIZE` output's `Module`
is not visible to a bare `require('./eden.js')` caller — drive it with
`vm.runInThisContext(src, {filename})` in global scope, not `require()` (see
[conventions-and-pitfalls.md](conventions-and-pitfalls.md) #5).

## `CMakeLists.txt` structure
- `web/tools/engine-sources.txt` (generated by `web/tools/gen-source-list.sh`) is the
  authoritative 81-file engine source list; `CMakeLists.txt` reads it and fails fast
  (`FATAL_ERROR`) on any `MISSING:` entry rather than silently dropping a file.
- `EDEN_SEAM_EXCLUDE` (line ~69) — the subset of that list compiled from a
  `src/seam/` replacement instead of the original; every entry has a comment
  explaining the "why" and which lever was used. This is the source of truth for
  "what's replaced" — see [architecture-overview.md](architecture-overview.md)'s
  lever table. Currently 15 files: `EAGLView.mm`, `EdenViewController.mm`,
  `EdenAppDelegate.mm`, `main.m`, `Texture2D.mm`, `FileArchive.mm`,
  `SimpleAudioEngine.mm`, `FileDownload.mm`, `FileUpload.mm`, `SharedList.mm`,
  `ShareUtil.mm`, `ShareMenu.mm`, `Alert.mm`, `Appirater.mm`, `md5.c`. Everything
  else in the list — including `FileManager.mm`/`FileManagerHelper.mm` — compiles
  as-is.
- `EDEN_DIAGNOSTICS` — option gating debug/diagnostic instrumentation, defaulted from
  `CMAKE_BUILD_TYPE` (ON for Debug, OFF otherwise) but independently settable so a
  release-shaped build can still carry diagnostics. When OFF: `DebugState_web.mm` is
  dropped from the source list entirely, the `[eden-p1]`/`[eden-gl-dbg]` prints and
  `eden_debug_tick` are `#ifdef`'d out, and `eden_gl_dbg_active()` returns `false`
  unconditionally — which also removes a per-draw `glGetError()` pipeline stall, not
  just print noise.
- `EDEN_ALLOC_TRACE` — **OFF, and a scratch-tree option only** (Phase M / M6). Adds
  `src/seam/AllocTrace_web.c`, which defines strong `malloc`/`free`/`calloc`/`realloc`/`memalign`
  over emmalloc's *weak* public symbols (no `--wrap`, no allocator replacement) and keeps a
  per-pointer table plus live bytes per captured callstack; `--profiling-funcs` is added so those
  stacks carry function names. It refuses to configure with `EDEN_THREADED=ON` (non-atomic
  counters) or outside Release (`-sMALLOC=emmalloc` is a Release-only link flag here). Drive it
  with `tools/headless-alloc-leak-probe.js`; it exists to answer "which call site is leaking",
  which is how M6 was found. Never ship it — it perturbs what it measures.

## Case-sensitivity and dedup gotchas (Linux CI vs. macOS dev)
- macOS's case-insensitive filesystem silently resolves quoted includes like
  `#import "Glu.h"` against `glu.h`; Linux does not. Fixed via generated relative
  symlinks for the known mismatches (`Glu.h`, `Input.h`, `Terrain.h`, `Vkeyboard.h`,
  `GLobals.h`) rather than editing the `Classes/` quoted include. Fixing the includes at
  source and deleting the symlink generator is now allowed (rule retired 2026-07-25) and
  would be a genuine simplification — the symlinks exist only to work around the old rule.
- `target_link_options` de-duplicates byte-identical list *elements* — every
  `--preload-file X@Y` argument starts with the same literal token, so without
  wrapping each one in `SHELL:` it silently collapses to a single preload and the
  rest vanish (surfaces as a stray "input file" link error, not an obvious warning).

## Linear memory: what actually sets the peak
*(measured 2026-08-31, ROADMAP Phase M / M1 — `node tools/headless-heap-ceiling-probe.js`, which
reports `eden_debug_heap().peakSbrkTop` from `src/seam/HeapProbe_web.mm` on a 20 ms sampling timer
through a scripted session. It is the only probe here that reports the **256z** ceiling; every
other memory number in this repo is a 64z number and is ~110 MB low.)*

| Phase | linear memory in use (`sbrkTop`) |
|---|---|
| menu, no world loaded | 93 MB |
| one 64z world loaded + saved | 116 MB |
| one 256z world, 5 teleport reload bursts, save | **232 – 251 MB** |

**Two conclusions, and the second one is the surprising one.**

1. **World *height* costs ~120 MB.** A 256z world roughly doubles linear memory over a 64z one,
   which the arithmetic predicts: the window arrays are runtime-sized by world height
   (`Classes/Terrain.mm`), so `blockarray` + `lightarray` go from ~21 MB at 64z to ~85 MB at 256z,
   plus 4× the `TerrainChunk` objects.

2. **World *count* used to cost ~22 MB each, permanently — fixed 2026-09-02 (Phase M / M6).**
   Every world load grew linear memory by ~22 MB that was never reclaimed, at both heights, with no
   plateau: reloading the *same* 256z world eight times walked `sbrkTop` from 240 MB to 426 MB in a
   dead straight line. It was a genuine leak, not fragmentation — four shim classes
   (`NSData`/`NSMutableData`, `NSArray`/`NSSet`, `EdenConcreteString`/`NSMutableString`) held C++
   ivars that this port's hand-written ObjC runtime never destroyed, because it emits no
   `.cxx_destruct` and `object_dispose()` is a bare `free()`. Each got a `-dealloc`; see
   [objc-runtime.md](objc-runtime.md), which now states the general rule.

   **The same torture run is flat across 8 loads at every height combination**, so world *count* is
   free again and peak is bounded by world size. Regression tests:
   `tools/headless-heap-ceiling-probe.js --torture=same256|height|same64` (must stay flat) and
   `tools/headless-alloc-leak-probe.js` (cheaper, and with `-DEDEN_ALLOC_TRACE=ON` it names the
   leaking call site). A ~20 KB-per-load residual remains, absorbed by the allocator.

The practical consequence: **peak linear memory is set by the biggest world the session opens** —
~222–233 MB at 256z. `-sMAXIMUM_MEMORY` is 512 MB, ~2.2× that ceiling. It shipped at 768 MB while
the leak was live (peak then depended on how many worlds were opened, and since the cap is a hard
abort, sizing it on one load would have converted a slow leak into a lost session) and came down
when M6 landed.

To read the current figure at any time: the dev console's `mem` command (backtick to open), or
`eden_debug_heap()` from a script.

## Non-optional build flags and why
- `-x objective-c++` — needed regardless of file extension for the ObjC++ sources.
- `-fobjc-runtime=gnustep-1.9 -fconstant-string-class=NSConstantString -fno-objc-arc`
  — see [third-party.md](third-party.md) for why gnustep-1.9 specifically (2.0 needs
  ELF/COFF sections wasm doesn't have).
- `-sINITIAL_MEMORY=100663296` (~96 MB) — the engine's static data alone is ~62 MB;
  `ALLOW_MEMORY_GROWTH` is a *runtime* knob and doesn't help at link time, so this has
  to be sized up front.
- `-sMAXIMUM_MEMORY=536870912` (512 MB) — **a hard cap: hitting it aborts the session**
  (`-sMALLOC=emmalloc` + the default `ABORTING_MALLOC=true`). Added by ROADMAP Phase M / M1
  (2026-08-31) to stop Emscripten's 2 GB default being baked into the module — in the threaded
  build that maximum is a *shared* `WebAssembly.Memory`, which cannot grow by realloc-and-copy, so
  the whole 2 GB is reserved as address space up front. **Do not read this as a footprint win:**
  M0 measured desktop WebKit committing that reservation lazily, so capping moved Safari's physical
  footprint by ~nothing. It is here for Blink (which charges committed `SharedArrayBuffer`
  differently) and for 2 GB devices that can fail a 2 GB *virtual* reservation.
  **It was 768 MB from M1 until M6 (2026-09-02)**, because at the time every world load leaked
  ~22 MB and peak was a function of session length rather than world size; with that leak fixed the
  512 MB the plan originally prescribed applies again (~2.2× the measured 256z ceiling). See
  "Linear memory: what actually sets the peak" below. `eden_heap_pressure_tick()` warns once at 80%
  and 90% so a cap abort is diagnosable.
- `-sSTACK_SIZE=8388608` (8 MB) — the wasm stack is carved out of `INITIAL_MEMORY`
  separately and defaults to 64 KB; `Terrain::render`'s ~380 KB of locals blows that
  default immediately.
- `-sUSE_ZLIB=1`.
- `-Wno-register -Wno-c++11-narrowing` — suppressing, not fixing, legacy C++98-isms in the
  2010-era engine sources. (These were unfixable while `Classes/` was off-limits; since
  2026-07-25 they are merely not worth fixing — the tables they silence are correct.)
- `TARGET_OS_IPHONE`/`BUILD_OGLES` — inherited from the shipped Xcode project's own
  preprocessor defines (reproducing its `project.pbxproj` settings), not a porting
  decision; `BUILD_OGLES` is the only path by which `CPVRTglesExt` reaches
  `Model.mm`, and implies `EGL_NOT_PRESENT` (this port's own honest addition — there
  is no EGL on web), which matters for how PVRT extension-pointer loading is stubbed
  (`src/seam/pvrt_matrix_palette.cpp` — see [gl-shim.md](gl-shim.md)).
- `-sSAFE_HEAP=2`, never `=1` — this port relies on unaligned memory access by design
  (wasm f64/i64 loads have no alignment requirement, exploited by the ObjC ivar-layout
  fix — see [third-party.md](third-party.md)); `SAFE_HEAP=1` faults on legitimate
  access. A `"Stack overflow! Stack cookie overwritten at 0x00000004"` message usually
  means a NULL-pointer write, not real stack depth — raise `-sSTACK_SIZE` to tell the
  two apart, don't assume the message is literal.
- `-x objective-c++` is genuinely required regardless of file extension — CMake's
  `LANGUAGE CXX` source property does **not** enable the ObjC frontend; an earlier
  wrong assumption here caused ~900 of 992 errors in one real build attempt.

## Release build
`-O2 -fno-strict-aliasing -sASSERTIONS=0` gets `eden.wasm` from 9.4 MB → 701 KB and
`eden.js` from 317 KB → 157 KB. Deliberately **not** taken: `-O3`/`-Oz`, `--closure 1`,
`-sENVIRONMENT=web` — the last specifically because it would break the `node
eden.js` headless gate used for fast iteration.

## Seam vs. wrap decision test
Before writing a new `src/seam/*_web.*` replacement for an engine file, grep whether
any *other, non-seam* engine file `#include`s the original header with quotes — quoted
includes ignore `-I` search-path ordering, so a seam replacement can only swap out the
`.mm`/`.cpp`, never the `.h`, when other kept files depend on that exact header (this
is why e.g. `Texture2D.h` is kept as-is and only `Texture2D.mm` is replaced). If only
one function inside an otherwise-fine file needs different behaviour, prefer
`-Wl,--wrap=` over forking the whole file (see `Movement_web.mm` wrapping
`Player::setSpeed`/`preupdate`, or `pvrt_matrix_palette.cpp` wrapping
`CPVRTglesExt::LoadExtensions`).
